# 从研究方向到完整 idea

产品的主要交付物是一个有新意、有意义、基本可行的研究 idea。第一部分直接回答**新问题是什么、为什么重要、idea 怎样解决它**，让背景、问题、动机和核心洞见一环扣一环，并说明与已有工作的具体区别。第二部分仅提供技术参考；默认不输出具体例子和实验计划。

完整 idea 以能够支撑 CCF-A 研究为构思目标：问题具体且重要，解释包含非显而易见的洞见，核心想法针对该洞见，扣除最近工作后仍有实质贡献，并能说明这会改变什么能力或科学认识。`map/propose` 用它比较与选择问题，`develop/refine` 让技术服务核心贡献，`review` 检查整条论证并提出具体改法。沿用现有调用与预算，不增加评分、审批或录用预测。

表达按与一位没有读过相关论文的研究者讨论来写：先说明谁遇到了什么困难，再展开原因、现有方法为什么不够，以及 idea 怎样改变这一点。必要术语在首次出现时解释，论文名称附带它实际做了什么。各部分允许用数句完整的话讲清逻辑，技术角度使用短问题作标题，具体条件放在正文。CLI 保留段落间隔；增加篇幅用于解释推理和操作，不补写例子或实验计划。

第一阶段先推导问题，再构思解决它的操作。`map` 的 `derivation` 连接“已有机制或现象线索 → 有意义的条件 → 困难如何产生或可能产生 → 对原目标的影响”。`prior_art_delta` 推演最接近方法在同样条件下会如何正常回应，以及为什么仍值得研究；`why_it_matters` 说明解决问题带来的能力或认识。机会记录用 `bottleneck_hypothesis` 保存可能的根本原因，用 `research_need` 保存由此产生的研究需要，替代原先提前要求解法的 `insight` 与 `feasibility_basis`。`propose` 才选择问题、构思想法，并通过 `idea_core` 和 `feasibility_sketch` 解释作用与基本可行性。

这两个任务使用 `Controller.ideation_context()` 准备的材料副本：保留论文方法、实验、结果、条件、分析疑点和引用，暂去掉阅读者生成的研究机会、对 idea 的建议及疑点中的实验建议。完整论文卡仍保存在项目中，第二阶段继续使用，避免单篇阅读时形成的小操作先替综合选题定方向。

这些判断在现有 `map → propose` 及后续讨论中完成。两类问题来源都允许尚无直接实验的合理猜想，也允许单篇论文提供关键启发；无需证明现有方法都有共同缺陷或全领域无解。对于已观察的困难，现象与原因的依据分开；对于推测的新困难，判断“推断为什么合理，如果成立为什么重要”，不要求它在关键假设错误时仍然存在。方法可以简洁，但问题的影响要连回原目标。审阅改善具体的推导或衔接，不因缺少实测否定问题，也不增加评分或审批。

第一阶段集中解决三个问题：具体研究贡献是否还有空间、方法是否有可预见的实施矛盾、相关论文是否真的回答了同一问题。创新比较分析动机、机制、信息和核心主张；论文的标题和作者声称的效果都不能直接替代正文与实验细节。构思直接使用主张分析，沿着“claim → 实验条件与控制 → 报告结果 → 可支持结论”理解最近工作，比较实质不同的研究切口，再提出最有价值的问题、动机和核心思路。不能因为某个小问题容易模拟，就优先把它扩成完整实验。

## 主流程

**第一阶段：Background → Problem → Motivation → Idea。** 按背景需要、已有工作进展、困难及可能原因、已有回应为何可能不足、研究需要、核心 idea 建立论证。`motivation.problem_origin` 只取两值：`unresolved_need` 从背景需求提出新的重要问题，解释现有主要思路难以跨过的障碍；`emerging_problem` 承认已有方法解决了原问题，再推导解决、使用或发展过程中暴露的新重要问题。两者均可基于已观察现象或合理推断。`problem_derivation` 在提出方法前讲清背景到问题的过渡，在 CLI 和主报告的 Problem 开头展示。

`existing_work` 保存已有进展，`research_need` 保存从局限推导的动机；`intervention` 总述准备作出的改变，`idea_core` 把核心想法展开为四段具体解释：

| 字段 | 要讲清楚的内容 |
| --- | --- |
| `concrete_target` | 谁使用什么对象、关系或信号；关系连接哪些对象、信号表达什么，具体改变发生在哪里。 |
| `construction_path` | 所需信息来自哪些可获得的输入，怎样提取、构造和核对；让读者看得出信息从哪里来。 |
| `capability_bridge` | 所提操作怎样改变模型面对的学习、推理或行动要求，为什么这一改变能带来需要的能力，并作用于前述问题。 |
| `essential_difference` | 最接近方法正常使用时已经能做什么，本想法具体改变了什么，以及这项差异为什么重要。 |

四段用平实的完整句子写入 Idea 正文，在 CLI 和主报告直接展示。内容可以具体到信息与作用过程，同时保持用户原本的研究方向；不强制落到某个数据集、训练任务或技术名称。它们在现有 `propose` 调用中形成，程序只检查必要内容是否齐全，沿用一次输出修复，不新增审查、评分或实验计划。

**动机的挖掘是第一阶段的核心工作。** `map` 在每个切口的 `derivation` 中，从背景需要与已有方法实际能力之间的差距，找出有意义的研究需要。可以分析现有假设在哪些条件下不再适用、什么重要关系尚未解释，或当前优化目标与真正需要的能力为何不一致；选择与材料相符的切口。`propose` 依据这条推导选择方向，用 `research_need` 说明需要理解或实现什么、为什么是由前述问题引出的，以及完成它会带来什么重要进展，再用 `why_this_method` 提出回应这一需要的 idea。动机应当在没有具体技术名称时仍然有说服力。

`propose` 的问题来源与所选切口保持一致。控制器将 `id/question/problem_origin/basis/derivation/prior_art_delta/why_it_matters/bottleneck_hypothesis/research_need` 九项保存为 `selected_opportunity`，把选题理由、推断性质、原因猜想和研究需要一同交给后续技术探索、设计和审阅。`review` 指出具体哪一步推断或衔接需要改进。修订可以合理调整问题及其来源，在 `review_responses` 解释并同步更新当前动机；最初快照保持不变。旧四字段和六字段快照仍可恢复、导出，不补造历史内容。沿用现有调用，不新增评分、审批或实验要求。

**第二阶段：Idea → Method（技术参考）。** 寻找可借鉴技术，说明为什么适合当前 idea、需要怎样改造。第一阶段的 `idea_core` 进入技术检索与设计；`develop/refine` 保留其具体解释，讨论改变想法时同步修改核心解释与动机，并记录理由。CLI 和主报告优先展示当前 `spec` 的选题推导与核心解释，还未形成技术方案时使用 `proposal`。旧保存内容缺少新字段时仍可导出，不补造问题来源或推导。第一阶段内部推演信息依赖与基本可行性；第二阶段也不以写出完整工程或实验协议为目标。

1. **理解输入。** 结合正式主题、最近八条用户补充和资源条件。讨论中的助手建议不会自动当成用户已经决定的方向。
2. **找到论文。** arXiv 的方法与策略默认看近十二个月，动机与贡献对照看近六个月，每次运行更新日期。会议按每个会议最新公开或收录论文的一届检索，本届未公开则取上一届，不受半年窗口截断；可用 `/date conference window` 改成日期筛选。已知的更早相关工作也参与对比。每个查询先取二十篇元数据，合并去重后按词项相关度和日期组织候选池，再用一次模型调用围绕实际研究问题筛选最多四十篇标题/摘要。记录选读原因和正文问题，全流程默认最多精读六篇，不为凑数阅读偏题文章。
3. **阅读已有工作。** 阅读者分别回答“有什么方法可借用”和“已有工作究竟回答了什么问题”。原文记录、实验范围、分析卡和研究启发完整保存；第一阶段的上下文副本暂不带入读者已经想到的方案。程序将可用于实验结果、作者明确局限的引用分组交给模型，并继续检查引用类型与来源；只有实际补读了新文本，才再次综合分析卡。
4. **第一阶段提出 idea。** `map` 先在少量不同的 `opportunities` 中保存问题推导、原因猜想、研究意义、已有方法回应和研究需要，不要求解决方案。通常两三个切口即可，最多四个，不为凑数生成。`propose` 比较研究价值，使用 `opportunity_id` 关联选中的主切口，并在 `selection_reason` 说明理由，再构思核心想法。`positioning` 对每篇最近相关工作写明已经解决什么、仍待回答什么、我们贡献什么；已知动机或贡献重叠在这一任务内修正。`feasibility_sketch` 推演可用输入到关键操作的路径，不能依赖隐藏答案、未开放接口或循环监督，也不能隐藏本来可见的信息来制造问题。资料暂少时仍可提出有意义的问题假设。
5. **第二阶段探索技术设计。** 先从 idea 与研究动机推导两个互补的技术问题，保存为 `design_axes`：为什么需要、必须实现的功能和方法检索方向。再形成最多三条查询，通过 `axis_ids` 对应这些问题，覆盖两个角度。技术问题不能只是“实现”和“评测”这样的通用标签。技术探索默认检索近十二个月的 arXiv 与各会议最新公开一届，可搜索其他计算机领域。优先复用已读材料，选中的新论文定向读取关键段落，最多三篇进入 `design_transfer`；每篇最多给三个真正有用的选择。只有出现具体未解问题才补读，不重复跑完整论文分析卡。已有方法可直接借鉴，重点是为什么适合当前问题、需要怎样修改。
6. **选择路线并交付。** 用 `design_decisions` 记录可借鉴技术、适用理由、改造方向和简单替代，并用 `axis_ids` 说明每个选择服务哪个技术问题；一种技术可同时服务两个角度。最终说明这些选择怎样共同实现 idea。保留关键实现条件即可，不生成实验计划。审阅者最多提出三个影响 idea 价值或可行性的意见，每条都有具体改法；设计者可采纳、调整、有理由地不采纳或指出能够区分解释的证据。默认初版加一次修订，`max_rounds` 控制这个讨论次数。最终 CLI 和报告以 idea 为主，技术参考为辅。

第一阶段的创新判断使用已读工作的具体动机、解释和贡献，方法相似可以作为借鉴；第二阶段以改善技术路线为目的。新文献若揭示明确矛盾，仍应据此改进方案，但不默认追加一整轮泛化查重。正式交付后不再自动启动搜索。

构思比较和最终写作沿用现有的 `map → propose` 两次调用，不新增一组评分或审批任务。技术角度规划复用第二阶段的 `plan_search` 调用；关闭联网检索或阅读名额已满时，仍规划技术角度并使用已有材料。程序检查来源 ID、切口关联、技术角度与查询/选择的对应及必要字段；问题是否有意义、差异是否构成贡献，仍需要模型依据论文内容进行科学判断。已有组件分别出现过，不等于它们共同揭示的问题已被回答；仅改名称、场景或指标也不自动成为新贡献。

## 跨领域技术如何进入方案

一篇来源论文通过这条记录进入设计：**要回答的设计问题 → 来源技术 → 两个问题的共同结构 → 原技术成立条件 → 本研究的改造 → 对动机的作用 → 简单替代**。

例如，其他领域的主动感知技术可能适用于为 agent 选择能区分环境规则的观察；需要明确共同的不完全观测结构、可计算信号和更新步骤，并说明相对简单替代路线的作用。最后按当前场景解释方法：解决哪个瓶颈、操作哪些对象和信号、怎样改造、为何这样改。借鉴记录是供设计者选择的技术选项，不是必须堆进方法的模块。原论文事实引用该论文的原文，迁移效果作为我们的预测。

## 角色如何交流

| 角色 | 收到什么 | 交给下一步什么 |
| --- | --- | --- |
| 阅读者 | 选中的论文片段、具体阅读问题 | 第一阶段：问题、动机和贡献边界；第二阶段：技术与迁移条件 |
| 构思者 | 用户方向、论文分析和原文 | 有贡献对照、连贯动机和基本实现路径的 idea |
| 设计者 | idea、技术借鉴、上一轮意见 | 可借鉴技术、适用理由、改造方向、逐条回应 |
| 研究讨论者 | 当前方案及共享文献材料 | 最多三个影响 idea 价值或可行性的具体意见及改进建议 |

每个任务都是配置后端的独立调用。当前角色串行运行，共用模型与调用预算；使用 Codex 时仍由本地 `codex exec` 执行。角色之间通过结构化材料交流。`review_responses` 将意见与采纳理由对应，`dialogue` 保存每轮交接，修订记录保存实际方法变化。

审阅总体认可 idea 时，仍可能提出具体修订；`next_action=revise` 连同实际意见或修订说明会交给设计者处理。已保存项目也能继续这类未处理的修订，仍受原有轮次、调用预算和重复内容停止条件约束。

下一轮讨论同时收到上一轮意见和修改记录，先检查设计者已经如何回应，再决定是否还有具体问题。可行性推演检查关键输入、信息流和明显矛盾；没有实验计划不会触发修复或阻止交付。兼容旧项目的实验字段可留空，已有实验记录保留在展开记录中。

意见不是命令。设计者可以说明一个批评为何不适用于当前问题，也可以指出决定该问题的证据；不能只回复“已解决”。方法相似不会自动淘汰 idea。若动机确实已有覆盖，可以在用户方向内重构问题或解释，并明确新预测。

## 研究质量要求

- 背景要导出问题：什么具体需求下，什么能力或理解被限制。
- 问题要值得研究：解决后增加什么能力、解释或可理解的边界，而非只有微小指标变化。
- 方法要必要：为什么它作用于原因；最简单可行替代能否同样解决问题。效率改善需要说明它解除的实际约束，不能只罗列 trade-off。
- 方法要对准原因：输入、输出、干预步骤与预期观察能连起来。
- 先检查 agent 已经能看到什么：若直接读取当前状态的简单策略即可完成任务，就要与它比较；若问题归因于旧经验干扰，也应考虑无旧经验的同一 agent。不能通过隐藏本来可见的信息来制造研究动机。
- 洞见要有区分力：内部比较最简单替代解释，说明核心想法增加的能力或理解。
- 构思要保留真实研究困难：不能为了容易实现，把重要问题换成人为小谜题，再用实验细节充当贡献。
- 借来的方法要说明来源；提出的假设可以大胆，但不能改写成论文已经报告的发现。

`motivation.basis` 区分论文已报告的困难与我们推演的问题。前者引用真实证据 ID；后者可以引用已有机制或现象作为前提，也可以没有引用。引用前提不等于新推断已获证实。正文自然说明一次“我们推测，在什么条件下，因为……会出现……”，随后展开动机与想法。所有引用仍检查来源身份与原文；名称、分数或表格完整度不能替代论证。

资源尚未测量时写明关键依赖条件。真正缺少的信号需要修改实现路径；模型不能把不可用信号直接写成可用。方案仍交付，同时写明具体替代设计。

## CLI 呈现

默认展示两个阶段和每一步的结论。第一阶段的 `[concept]` 展示 idea、动机与贡献对照、基本可行性；第二阶段的 `[design]` 展示技术借鉴、路线选择及原因；最后 `[idea]` 展示完整研究方案。`[skill]` 用中文说明分析方法，`[paper]` 给标题与来源，`[evidence]` 给原文依据；同一依据不在每一步反复刷屏。第二阶段检索和阅读不会再显示成第一阶段。

最终报告明确分成两部分。第一部分解释 idea，回答“新问题是什么、为什么重要、Idea 怎样解决它”；第二部分只给技术参考、适用理由与改造方向，不重复第一部分的三个问题，也不提供具体例子或实验计划。内部可行性推演可以用 `/details` 查看。技术参考逐项显示采用什么、选择理由和针对本场景的改造。正文直接给出主张、选择和理由，去掉“尚未确认”这类泛化措辞；影响方案的具体条件写进输入或设计选择中。小标题与字段重点使用颜色，正文保持正常文字。论文标题与链接直接跟随相关结论，完整分析也将内部引用转换为可读来源。

- `/config` 显示可读的模型、日期、会议、选文规模和预算。
- `/details` 展开上一步完整分析；`/details on` 显示完整过程，`off` 恢复易读视图。
- 底部三行分别显示模型与进展、调用与时间预算、使用介绍与操作入口。新建交互项目允许单次模型调用等待 20 分钟；总预算仍独立计时，超时提示给出调整与恢复命令。
- 运行时隐藏输入框，Ctrl+C 停止，之后 `/run` 继续。
- 恢复时缓存步骤只提示“已复用”，旧引文不重复刷屏；新分析正常显示，完整旧结果仍可通过 `/details` 和 `/evidence` 查看。
- 累计时间耗尽和单次调用超时分别提示：前者调整 `max_seconds`，后者调整 `timeout_s`；成功检查点保持可恢复。

第一阶段 idea 先保存，再进入技术探索；每项技术借鉴完成后保存，技术参考生成后再保存，随后讨论对 idea 有实质影响的问题。中断时交付已有构思或方法草稿。恢复保留第一阶段来源集合，第二阶段新增论文不会被倒回初轮完整精读；已选论文的下载继续，不重新规划和筛选。相关来源或指导文本变化时重新计算对应任务。修改构思规则时，未改变的正文阅读仍可复用。

会议 PDF 不可用时，可以在本次获取预算内查找同标题的公开预印本；来源记录包含实际阅读版本。全文获取失败按论文 ID 在当前轮去重，补全链接不会触发重复下载。

## 验收方式

自动测试覆盖：资料稀少仍提出假设方案、第一阶段贡献对照与基本实现路径、技术借鉴先于详细设计、第二阶段定向阅读和来源复用、跨论文引用拒绝、具体阅读缺口的有限补读、两种日期窗口、检索与下载中断恢复、意见逐条回应，以及终端的阶段、预算和常驻入口。合成后端用于流程测试；真实模型输出另作运行检查。
